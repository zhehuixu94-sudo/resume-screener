## 1. 定稿结论

| 项 | 定稿值 | 说明 |
|---|---|---|
| `pass_line` | **60** | 兜底线；`reject_threshold() = pass_line − band_width = 55` |
| `auto_pass_line` | **70** | **生效达标线**（显式优先于 `pass_line + band_width`）|
| `band_width` | **5** | 兜底带；仅在未写 `auto_pass_line` 时才决定达标线 |
| 加分项变体 / `γ` / `scale` | **W1（残差 ln n + 0.25·expl）· γ=0.05 · scale=25** | 维持现状，不动 |
| `scoring_semantics` | `g2_scale25_budget25` | 公式版本（`config_version` 只管参数，管不了公式）|

**生效三档 = ≥70 自动达标 / [55,70) 转人工 / <55 才进入「可自动淘汰」的判据**（还要再过双通道 + 硬门槛 + 冲突检测）。

**必须写清的两条口径（防误读）**：

1. **同一个「线」有三张脸**：`pass_line`（60）· `pass_line + band`（65）· `auto_pass_line`（70）。
   代码取值顺序（`app/contracts/job_config.py:174-181`）是 **显式 `auto_pass_line` 优先**，因此**生效达标线 = 70，不是 65**。
   配置里 `band_width` 的字段说明按字面写的是「≥线+band 自动达标」，**与 70 打架**——以 `auto_pass_line` 为准，本文即该冲突的仲裁记录。
2. **绝不能写「线以下都淘汰」**：实测 310 份里分数 <55 的有 **179 份**，真正落 `auto_reject` 的只有 **33 份**，
   其余 **146 份转人工**。差额不是隐藏缓冲，是「宁可多转人工、不接受不可逆的自动淘汰」的代码级实现
   （`app/pipeline/rules.py:224-345`：硬门槛 veto、方向不符且低分、边缘+低分开关命中，四类才自动淘汰，其余一律转人工）。

**实测兜底数（纪律「设定值 = 生效值」的验证）**：`auto_pass` 74 件的分数下界 **70.85 ≥ 70**，
`manual_review` 203 件的上界 **69.40 < 70** ⇒ 达标线无内部余量，界面上写的 70 就是实际生效的 70。

## 2. 依据：四判据交集 = 空集（原始数）

四判据（`out/scan_joint_criteria.py`，γ 6 档 × 变体 × scale 15…80 步长 2 全扫）：

| ② | 加分项与条数的相关 | **\|ρ\| ≤ 0.3** | 防止「加分项在奖励条目多」 |

| γ·变体 | \|ρ\| | 红线最小可行 scale | 该点重叠 | 三判据最大 scale | 该点最小余量 |
|---|---|---|---|---|---|
| 0.00C 桶内 nb=8（resid+0.25e） | 0.02 | **23** | **0.69** | **21** | **+2.81** |
| 0.05C 桶内 nb=8 | 0.02 | 25 | 0.69 | 23 | +2.68 |

## 3. 为什么不「放宽一条判据」（零一纪律审查意见，2026-09-26 06:50，全文见 `out/scratch/align_20260926/零一-纪律审查意见-20260926-0650.md`）

1. **放宽①（3.2 → 2.8）＝ 明知有破线概率还叫它过**。3.2 不是拍的，是同配置重复跑实测的极差上限；
   降门槛等于重现 2026-09-18 被否掉的 A 方案（余量 +0.13）的老错：「选 A 是假装红线过了，不是真过」。
2. **放宽③（0.7 → 0.69）＝ 事后凑参数**。扫描已证明单独放任何一条都凑不出可行点（放③则余量还差 0.39，放①则重叠还差 0.01），
   两条一起松就是**为了让结论成立而改判据**。
3. **要给「0.69 够用」找依据，得先有人工锚点**。顺序不能反：**先过 gate，再谈放宽**。

**⇒ 交集空集本身就是结论：当前口径下自动校准不可用，真实动线只能走人工锚点标定（`anchor_calibrated`）。**
这与 `docs/定稿决策-20260918.md` §十一 的原话结论一致，不是新发明。

## 4. 被否掉的替代方案（记录在案，避免重复劳动）

### 4.1 抬自动淘汰线到「淘汰 70%」

（反直觉但必须写明：**这条线并没有误伤「明显合格」**，75 份只掉 1 份；它把保留区误放从 10 压到 2。）

**但它破红线**（原始穿越表）：

| R 成员 | 现库分 | 55 线 | 58.2 线 | 62.33 线 | 63 线 |
|---|---|---|---|---|---|
| real_a_deg1 | 67.39 | 保留 | 保留 | 保留 | 保留 |
| real_b | 62.78 | 保留 | 保留 | 保留 | **淘汰** |

与「宁可多转人工」的优先级纪律正面冲突。**该路径排除。**

### 4.2 候选 B「配额 + 显式豁免」

⇒ **归入《待锚点清单》备选，需用户明确点头才可实装**，今天不做。

## 5. 与 `config/` 的关系：为什么决策记录进 `docs/` 而不是写进 config 的 `notes`

09-18 §七留了一个洞：「决策没有进 config」。本次**不用改动 config 的方式补它**，理由是实测的机制：

- `tests/test_final_package.py:164` 断言 **`snap["config"] == raw`**（快照内嵌配置**逐字**）⇒ **改 notes 就必须同批重冻快照**；
- 重冻会让 `config/job_hr_admin.json` 的 **sha256 从 `804c4e53…541` 变成新值**，而这个哈希正是两侧共同的「口径未动」证据锚点
  （零一 2026-09-26 审查文件与赫尔墨斯状态基线都用它）；
- `code_fingerprint` 只覆盖 5 个流水线文件（`weighted_total` / `score` / `rules` / `honesty` / `rescore`），**不含 config 本身**，
  所以「为 notes 一个新哈希」付出的证据链代价大于收益。

**规则（写死，避免下次争）**：
- **纯说明性内容** → 进 `docs/`（本文），config 的 sha256 保持不变，两侧的哈希锚点继续有效；
- **一旦真要改数值口径**（例如 `auto_pass_line` 70 → 62.3）→ **必须**改 config + 同批 `tools/freeze_config_snapshot.py` 重冻 + `pytest` 全绿 +
  把新哈希写进本文与交付文档。这条是纪律「口径变更必须同批次冻结快照」的落地。
